# 架构决策记录（ADR）

本文件记录当前从项目设计资料中提炼出的架构决策。标记为“暂定”的决策可在 POC 证据出现后修改；修改时保留原记录和替代原因。

## ADR-001：以教材驱动的学习文档生成为项目边界

- **状态**：已采纳（第一阶段）
- **背景**：项目用于个人学习和技术练习，需要一个可控但足够真实的多 Agent 场景。
- **决策**：系统的主要输入是一本或多本教材，主要输出是可在线学习、练习和复习的文档，不扩展为通用教育平台、知识库或课程市场。
- **后果**：所有架构能力都必须能回到教材理解、内容生成或质量检查；账号、协作和大规模运营延后。

## ADR-002：Learning Blueprint 作为规范化中间层

- **状态**：已采纳（暂不锁定存储形式）
- **背景**：下游 Agent 不应分别重新理解整本教材，且需要共享知识结构和来源。
- **决策**：教材理解输出 Learning Blueprint，课程编排和内容 Agent 原则上以蓝图为共同上下文。
- **后果**：蓝图成为核心 artifact 和质量门；需要版本、来源、依赖和状态；具体 Schema、数据库或图实现保持开放。

## ADR-003：知识单元而非页面作为主要内容粒度

- **状态**：已采纳
- **背景**：目录和页面不能充分表达概念、定理、例题、证明及其依赖。
- **决策**：以 Knowledge Unit 组织内容，页面只是最终呈现形式。
- **后果**：可按知识单元生成讲解、测验和来源关联；呈现层不能反过来决定知识模型。

## ADR-004：主教材 + 补充教材的多教材角色模型

- **状态**：已采纳（多教材功能本身为 P1）
- **背景**：多教材不能简单拼接或只取交集，且需要处理深度、组织方式和冲突差异。
- **决策**：指定主教材作为学习路径骨架，其他教材用于补充、替代解释、例题和拓展；保留各自来源和差异。
- **后果**：必须存储来源角色和映射关系；冲突不得被静默合并；单教材 POC 不应为多教材实现过度设计。

## ADR-005：外部资料只做补充和核查

- **状态**：已采纳
- **背景**：教材可能缺少背景或需要事实检查，但项目不希望失去教材课程主线。
- **决策**：外部资料可以补足前置知识、应用或核查事实，不能无标记地取代教材内容。
- **后果**：外部内容必须携带来源和角色标记；审核需要区分教材一致性与外部事实支持。

## ADR-006：按职责定义 Agent，允许实现时合并

- **状态**：已采纳
- **背景**：项目要练习 Agent 编排，但 Agent 数量本身不是目标。
- **决策**：保留教材理解、课程编排、讲解、背景补充、交互、测验和审核等职责边界；是否由独立 Agent、同一模型的不同步骤或普通函数实现，留给实验决定。
- **后果**：契约和验收比进程数量更重要；过早拆分会增加状态和调试成本。

## ADR-007：质量审核是发布链路中的一等阶段

- **状态**：已采纳
- **背景**：生成内容可能出现事实、逻辑、公式、遗漏和衔接问题，也可能涉及学术分歧。
- **决策**：内容必须经过审核；问题要可定位、可回退、可重生成或交给人工，不得静默覆盖。
- **后果**：每个 artifact 需要审核状态和问题记录；发布策略要区分通过、带风险和阻塞。

## ADR-008：第一阶段采用单学科单章节 POC

- **状态**：已采纳
- **背景**：项目需要先验证完整闭环，避免同时承担多学科、多教材和平台建设复杂度。
- **决策**：第一阶段选择一门可验证性较强的学科（建议数学分析）和一章内容，跑通导入、蓝图、讲解、测验、基础审核与在线呈现。
- **后果**：评估样本小而深；多教材、复杂交互和高级自动评估排在后续；架构仍需留下扩展边界但不提前实现。

## ADR-009：显式 artifact、版本和来源追踪

- **状态**：已采纳（语义层）
- **背景**：需要检查、回溯、比较和重新生成，且教材来源是系统可信度基础。
- **决策**：教材引用、蓝图、生成内容、审核结果和最终文档都视为可区分 artifact，携带运行/版本/来源关系。
- **后果**：重生成不能删除旧版本；存储方案可变，但追踪语义不可省略。

## ADR-010：第一阶段采用人工 + 自动检查的混合评估

- **状态**：已采纳（第一阶段）
- **背景**：项目首先验证内容质量，复杂自动指标尚未有可靠基线。
- **决策**：用固定知识点样本、规则/自动检查和小规模人工评审共同验收覆盖、正确性、学习路径、测验覆盖和在线学习适配性。
- **后果**：需要建立标注 rubric 和回归样本；不能用单个模型评分替代人工判断。

## ADR-011：技术实现保持供应商和基础设施中立

- **状态**：部分保留，具体选择已由 ADR-013 至 ADR-018 收敛
- **背景**：现有设计明确未固定解析器、RAG、Schema、模型、Agent 框架、数据库和前端。
- **决策**：保留“通过适配边界实现可替换”的原则，但第一阶段已经确定 Vue/FastAPI/LangGraph/PyMuPDF/SQLite/ModelProvider 等默认实现。具体技术选择分别记录在 ADR-013 至 ADR-018 和 `docs/technology-selection.md`。
- **后果**：不会为了抽象而拒绝 POC 所需的具体实现；领域模型仍不直接绑定 OpenAI、Ollama、vLLM、数据库驱动或前端组件库的供应商细节。

## ADR-012：不确定与学术分歧必须显式标注

- **状态**：已采纳
- **背景**：项目要求标注事实风险点和存在学术分歧的立场性表述，但不越权替用户下结论。
- **决策**：把不确定、冲突、学术分歧和待人工判断作为内容/审核状态的一部分。
- **后果**：在线文档需要展示风险标注；“没有发现问题”不能被解释为绝对正确。

## ADR-013：以 JSON Document IR 作为学习文档规范输出

- **状态**：已采纳（第一阶段）
- **背景**：Markdown/HTML 不能完整表达知识单元、来源、审核状态、测验和受控交互。
- **决策**：Agent 输出经过 Pydantic 校验的 JSON Document IR；Vue renderer 负责把 IR 映射为受控组件。Markdown 仅作为文本块或导出格式。
- **后果**：内容与呈现解耦，支持局部重生成、版本比较和来源追踪；需要维护 IR Schema 和 renderer 的节点白名单。

## ADR-014：Vue 主应用采用 shadcn-vue 与 Tailwind CSS

- **状态**：已采纳（第一阶段）
- **背景**：项目维护者熟悉 Vue，且不希望 Agent 从头生成基础 CSS 和通用组件。
- **决策**：使用 Vue 3 + TypeScript + Vite，组件采用 shadcn-vue 的源码组件方式，样式采用 Tailwind CSS；领域组件由项目维护者组合和维护。
- **后果**：AI 辅助开发集中在组件组合和领域逻辑；不直接使用 React 版 shadcn/ui；需要约束主题 token、无障碍和组件修改方式。

## ADR-015：P0 采用 PDF + PyMuPDF + SQLite FTS5 输入检索路线

- **状态**：已采纳（第一阶段）
- **背景**：单章节 POC 首先需要可靠的来源定位，而不是大规模语义检索基础设施。
- **决策**：P0 只处理文本型 PDF，使用 PyMuPDF 建立页/块级 SourceBlock 和 SQLite FTS5；暂不引入向量数据库。
- **后果**：实现简单、来源清晰、易于调试；扫描 OCR、embedding 和语义召回需要后续任务和证据支持。

## ADR-016：模型接入统一为 OpenAI 与 OpenAI-compatible 两类 Provider

- **状态**：已采纳（第一阶段）
- **背景**：项目需要同时试验云端 OpenAI API 和本地模型服务。
- **决策**：领域层依赖 `ModelProvider`；实现 `OpenAIProvider` 和 `OpenAICompatibleProvider`，后者连接 Ollama 和 vLLM 的兼容接口。Provider 必须声明结构化输出、工具、流式和视觉能力。
- **后果**：可以切换云端与本地模型；不能假定兼容接口在所有模型上的能力完全一致，运行前必须做 capability check。

## ADR-017：P0 使用 FastAPI + 本地 worker，不引入分布式队列

- **状态**：已采纳（第一阶段）
- **背景**：POC 规模小，主要风险在内容质量和 artifact 流程，而不是任务吞吐。
- **决策**：FastAPI 提供 API，LangGraph 在本地 worker/CLI 执行，SQLite 保存运行和 artifact 元数据；暂不引入 Celery、Redis 或 Kafka。
- **后果**：部署和调试简单；未来扩展并发时替换 worker 调度，不改变 API、artifact 和 Provider 契约。

## ADR-018：VitePress 作为可选静态导出目标，而非主前端

- **状态**：已采纳（第一阶段）
- **背景**：VitePress 擅长 Markdown 驱动的静态站点，而本项目主界面还需要运行状态、审核、版本和来源交互。
- **决策**：主前端使用 Vue SPA；未来可以把已接受的 JSON Document IR 导出为 Markdown + frontmatter，再由 VitePress 发布静态快照。
- **后果**：内部动态工作流不受静态构建限制，同时保留文档发布能力；需要维护 IR→Markdown 导出器。
