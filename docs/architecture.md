# Annotation 架构设计

## 1. 架构目标

架构服务于一个可验证的 POC：将教材理解为 Learning Blueprint，再以蓝图为共同上下文生成、审核并整合学习文档。设计重点是边界、可追溯性和可迭代性，而不是预先构建完整平台。

## 2. 目标 repository structure

```text
/
├── AGENTS.md                         # AI/开发协作约定
├── README.md                         # 仓库入口（后续应链接设计与运行方式）
├── docs/
│   ├── requirements.md               # 需求、范围、契约与不变量
│   ├── architecture.md               # 组件、数据流、接口和边界
│   ├── technology-selection.md       # 前后端、Agent、模型和输入输出技术路线
│   ├── decisions.md                  # 架构决策记录（ADR）
│   └── evaluation.md                 # 评估方案、指标和验收门槛
├── tasks/
│   └── backlog.md                    # 有序任务、依赖和完成定义
├── documents/
│   └── ai_textbook_project_docs/     # 原始设计资料与项目背景
├── src/annotation/                   # Python API、领域模型、工作流、适配器
├── web/                              # Vue 3 + TypeScript 前端
├── tests/                            # 单元、契约、流程和回归测试
├── evals/                            # 固定评估样本、标注、评分结果
├── artifacts/                        # 本地/构建生成物（不作为源代码）
```

本轮只建立设计和任务文档，不创建 `src/`、`web/`、`tests/`、`evals/` 或 `artifacts/` 的业务实现。`documents/ai_textbook_project_docs/` 是现有设计资料目录，不能被当作运行时输出目录。具体技术选型见 `docs/technology-selection.md`。

## 3. 逻辑组件

### 3.1 输入与教材解析层

第一阶段接收文本型 PDF、学习目标、学习对象和范围，使用 PyMuPDF 建立页/块级定位、可检索片段和来源引用。解析器应把“原始内容”和“派生片段”区分开；OCR、EPUB、HTML 和复杂版面作为后续适配器。

### 3.2 教材理解 Agent

负责识别章节结构、知识单元、教学材料、前置关系、重点和多教材映射，输出 Learning Blueprint 草案，并执行覆盖与关系检查。它不是简单的目录抽取器。

### 3.3 Learning Blueprint 存储/版本层

保存蓝图及其来源、状态、版本、检查结果和待解决问题。它是教材理解与下游内容生成之间的规范化边界。第一阶段使用 Pydantic 模型、SQLite 元数据和版本化 JSON artifact；后续仍可迁移到 PostgreSQL 或其他存储。

### 3.4 课程编排层

根据学习目标和蓝图规划内容任务，决定调用哪些专用能力、任务顺序、验收标准和回退路径。第一阶段使用 LangGraph 保存流程状态和 checkpoint；不应把所有知识重新塞进每个 Agent 的隐式上下文。

### 3.5 专用内容 Agent

- **讲解生成**：围绕蓝图单元写出学习者可读的解释、衔接和示例。
- **背景补充**：补齐理解所需的前置、术语、应用或直观解释，并标记外部来源。
- **交互内容**：按知识特点提出图表、可视化或交互模块，不强制每点生成。
- **测验生成**：根据单元目标和学习路径生成练习与测试，并记录覆盖关系。
- **审核**：检查事实、逻辑、公式/定义、覆盖、衔接、教材一致性和学术分歧，输出可定位的问题。

这些是职责边界，不是必须独立部署的进程或模型。实现时可以合并，只要输入、输出和审核边界仍清楚。

### 3.6 内容整合与呈现层

将经过审核的讲解、例题、补充、图表、交互和测验按蓝图学习路径组合为 JSON Document IR，再由 Vue 3 + TypeScript + shadcn-vue + Tailwind CSS 的 renderer 展示来源、风险标注和版本信息。VitePress 仅作为未来的静态导出目标。

## 4. 规范化 artifact 流

```text
Source Material
   ↓ 解析、定位、索引
Source References
   ↓ 抽取、对齐、检查
Learning Blueprint (draft)
   ↓ 完整性/冲突检查
Learning Blueprint (accepted)
   ↓ 规划、委派
Content Artifacts (explanation / examples / quiz / digital)
   ↓ 审核、修订、人工介入
Reviewed Content Set
   ↓ 整合
Online Learning Document
```

每一步都应携带最小元数据：`artifact_id`、`run_id`、`version`、`source_refs`、`status`、`created_by`（Agent/人工）和 `issues`。字段名只是语义建议，不是当前实现 Schema。

## 5. 组件间边界

| 边界 | 输入 | 输出 | 关键约束 |
|---|---|---|---|
| 解析 → 理解 | 可定位教材片段、章节元数据、用户目标 | 蓝图草案 | 不把无来源摘要当作教材事实 |
| 理解 → 编排 | 已检查或明确标记状态的蓝图 | 内容任务计划 | 任务必须引用蓝图单元和验收条件 |
| 编排 → 内容 Agent | 单元、目标、来源、上下文限制 | 内容 artifact 草案 | Agent 不应自行改写主学习路径 |
| 内容 Agent → 审核 | 草案、来源、蓝图关系 | 问题、判定、修订建议 | 问题可定位且不可静默丢弃 |
| 审核 → 整合 | 通过/带风险/待人工内容 | 可呈现文档 | 发布策略区分通过、风险和阻塞 |

## 6. 状态与失败处理

建议使用显式状态而非隐式成功：`draft → checking → accepted / needs_revision / blocked → published`。解析失败、蓝图覆盖不足、来源冲突、生成质量不达标和审核超时都应产生可见失败记录。

重试应区分“同一输入的技术重试”和“修改提示/蓝图后的新版本”。禁止用新输出覆盖旧输出而失去比较能力。是否自动重试、最大轮数和停止条件由实现阶段根据实验确定。

当前 POC 已落地一条最小 LangGraph 图：`ingest → load_or_create_blueprint → generate_document_ir → validate_document_ir → review → assemble`。图状态显式携带蓝图、文档、来源、provider 元数据和错误列表；蓝图节点在进入内容生成前执行确定性的覆盖、来源和前置关系检查；默认使用 Mock Provider，真实模型通过 `ModelProvider` 工厂替换。教材导入后可写入本地 SQLite FTS5 索引，并通过 `source_ref` 返回页/块证据。该图用于验证 artifact 传递和状态边界，不代表完整多轮教材理解/内容审核闭环已完成。

## 7. 运行与部署假设

- 第一阶段可采用单机或单进程编排，以降低实验成本；没有生产级高可用承诺。
- Agent 可以共享一个编排运行上下文，但核心 artifact 通过显式契约传递。
- 长任务应可恢复或至少保存阶段性产物；“从头再跑”不是唯一故障恢复方式。
- 模型、检索、解析和呈现服务均视为可替换适配器；不在架构层锁定供应商。
- 需要外部资料时，应经过显式检索/引用路径，并标明其补充或核查角色。

## 8. 安全、版权与治理假设

- 用户对输入教材拥有使用权限，或项目运行在已获授权的材料上。
- 系统保留来源和审核记录，不设计规避访问控制、版权限制或删除署名的流程。
- 不确定、存在学术分歧或来源冲突的表述应被标注，系统不越权替学习者作立场性结论。
- 运行日志可能包含教材片段和生成内容，后续实现需单独决定脱敏、保留期限和访问控制。

## 9. 明确不固定的技术选择

仍需通过实验决定：扫描 PDF 的 OCR 方案、语义 chunk 策略、是否引入 embedding/向量数据库、具体模型名称、循环最大轮数、部署平台和自动指标实现。已确定的技术边界、模型适配器和前端路线见 `docs/technology-selection.md`。

## 10. 架构假设清单

以下假设是当前结构成立所依赖的前提；如果其中任何一项不成立，应先更新需求和 ADR，再调整实现：

1. 用户提供的教材可合法处理，并且至少能保留文档、章节、页码或等价的来源定位。
2. 教材是课程主线和首要事实来源；外部资料不会在没有标记的情况下替代教材。
3. 一章内容可以被拆分为可复用的知识单元，且知识单元之间存在可表达的前置、相关或支撑关系。
4. Learning Blueprint 足以作为教材理解与大部分下游生成之间的共享上下文；下游不需要每次重新理解整本教材。
5. 蓝图可以表达章节层级、知识类型、教学材料、学习顺序、来源和不确定性，而不依赖特定数据库或图实现。
6. 生成讲解、补充、数字内容和测验都能关联到一个或多个蓝图单元及其来源。
7. 内容质量可以通过“自动结构检查 + 人工抽样/审核”在小规模 POC 中得到有意义的判断；单一模型分数不是充分证据。
8. 审核发现的问题可以被定位、分类，并通过修订、重生成或人工介入处理；失败不需要静默吞掉。
9. 运行可以保存阶段性 artifact、版本和状态，因此长任务不必总是从零开始，旧结果也不会被新结果覆盖。
10. 第一阶段的并发量、教材规模和用户数量较小，单机或单进程编排足以支持实验，不要求生产级高可用。
11. Agent 的职责可以通过显式 artifact 契约隔离，即使多个职责最终由同一模型、进程或函数实现。
12. 解析、检索、模型、存储和呈现都可以通过适配边界替换；当前没有必须绑定的供应商或基础设施。
13. 在线文档至少需要展示学习路径、来源和风险标注；具体页面形态不会改变领域模型。
14. 对存在学术分歧或事实不确定的内容，系统可以标注风险并把最终判断留给学习者/人工评审，而不是要求 Agent 自动裁决。
15. OpenAI API、Ollama 和 vLLM 可以通过统一的文本/结构化输出适配器接入；不同模型能力差异可以通过 capability check 暴露。
16. Vue 前端可以用 JSON Document IR 驱动受控组件渲染，且 shadcn-vue/Tailwind CSS 足以覆盖 P0 的阅读、来源、审核和测验界面。
17. VitePress 的静态构建适合作为已接受文档的发布目标，但不需要承载 P0 的运行状态和审核工作台。
15. 多教材、交互内容和复杂自动评估可以在单教材单章节闭环之后扩展，不会反过来成为 POC 的隐含前提。
