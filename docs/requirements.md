# Annotation 需求规格

## 1. 目标与问题定义

Annotation（书注）要验证一种教材驱动的学习内容生产能力：给定一本或多本学科教材，系统能否理解其中的教学结构和知识关系，并生成一份比直接阅读原始教材更适合在线学习、练习和复习的文档。

项目的核心产物不是目录摘要，而是围绕 Learning Blueprint 组织的学习内容。系统需要保留教材来源、学习顺序、前置依赖和审核痕迹。

## 2. 目标用户

- 学生和自学者：需要结构化、可解释、可复习的学习材料。
- 基础薄弱的入门者：需要术语解释、前置知识和循序渐进的衔接。
- 项目维护者：需要通过真实但可控的场景练习多 Agent 内容生成流水线。

第一阶段优先服务项目维护者和一个小规模的学习者试用场景，不承诺面向大规模公共用户。

## 3. 范围

### 3.1 第一阶段必须完成

以一门学科的一章为 POC，完整跑通：

1. 导入教材并建立可检索的内容引用；
2. 识别章节结构、知识单元和教学材料；
3. 生成 Learning Blueprint；
4. 检查蓝图的覆盖、关系和来源完整性；
5. 按学习路径生成知识讲解；
6. 生成与核心知识对应的例题、练习或测验；
7. 对内容进行基础事实、逻辑、完整性和教材一致性审核；
8. 整合为可在线阅读的学习文档，并展示来源与必要的风险标注。

### 3.2 设计上支持但不作为第一阶段验收前提

- 多本教材：指定主教材，其他教材作为补充并保留差异和来源；
- 背景知识、应用、图片、图表和交互内容；
- 生成—评价—修改、调研—补充—核查、规划—委派—验收等 Agent loop；
- 人工审核和用户反馈闭环；
- 更细粒度的自动评估和多学科适配。

### 3.3 明确不在第一阶段

- 账号、权限、协作和社区功能；
- 移动端原生应用；
- 通用教育平台、通用知识库或课程市场；
- 大规模并发、生产级多租户和长期运维；
- 预先承诺特定模型、向量数据库、图数据库、解析器或前端框架。

## 4. 领域对象与契约

### 4.1 教材（Source Material）

用户上传的一本或多本教材及其章节定位信息。教材是课程主线和事实核查的首要来源。输入格式（PDF、EPUB、HTML 等）暂不固定，但必须能保留文档、章节、页码或等价定位信息。

### 4.2 知识单元（Knowledge Unit）

内容组织的主要粒度，可表示概念、定义、定理/命题、公式、方法、例题、证明/推导、应用、易错点或补充知识。知识单元不能简单等同于页面或目录项。

### 4.3 Learning Blueprint

教材理解与内容生成之间的规范化中间层，至少表达：

- Chapter / Section 层级；
- 知识单元及类型；
- 核心思想、前置条件和相关单元；
- 例题、证明、推理和其他教学材料；
- 主教材或补充教材来源；
- 学习重点、建议顺序和未解决的问题。

具体 JSON Schema、数据库表或图结构暂不在需求层固定，但任何实现都必须满足上述语义。

### 4.4 学习内容文档

围绕蓝图学习顺序组织的讲解、例题/证明、补充、练习/测验和数字化内容。内容可以有选择地包含图片、图表或交互，不要求每个知识单元都生成全部形式。

### 4.5 审核结果

记录事实风险、逻辑问题、公式/定义问题、知识遗漏、衔接问题、教材冲突和学术分歧等发现；结果应能关联到具体内容、蓝图单元和来源。

## 5. 功能需求

| 编号 | 需求 | 优先级 | 验收要点 |
|---|---|---:|---|
| FR-01 | 接收一本或多本教材及可选学习目标、学习对象、范围 | P0 | 输入可被定位、分块并引用 |
| FR-02 | 提取章节和教学结构，而非仅复制目录 | P0 | 能说明章节问题、知识衔接和教学材料 |
| FR-03 | 生成带来源和依赖的 Learning Blueprint | P0 | 关键知识单元、前置关系和来源可检查 |
| FR-04 | 支持蓝图完整性检查和回退修正 | P0 | 发现遗漏、错误合并或冲突后可回到抽取阶段 |
| FR-05 | 基于蓝图生成按学习路径组织的讲解 | P0 | 内容覆盖关键单元并能解释衔接 |
| FR-06 | 生成与知识单元对应的例题、练习或测验 | P0 | 测验覆盖核心知识且可追溯 |
| FR-07 | 对生成内容进行基础审核并支持重生成/人工介入 | P0 | 问题可定位，审核不被静默覆盖 |
| FR-08 | 输出可在线阅读的学习文档 | P0 | 内容结构清晰，来源和风险标注可见 |
| FR-09 | 补充背景、应用、图表或交互内容 | P1 | 内容与蓝图单元建立关系并标注来源/生成状态 |
| FR-10 | 对多教材进行主次对齐而非机械拼接 | P1 | 保留组织差异、深度差异、冲突和补充关系 |
| FR-11 | 支持运行、版本和 artifact 的可追踪性 | P1 | 可知道由何次运行、何版本蓝图产生 |

## 6. 非功能需求

- **可追溯性**：关键内容必须能从在线文档追溯到蓝图、教材片段和审核记录。
- **正确性优先**：宁可标记不确定或交由人工审核，也不应无依据地给出确定结论。
- **教材一致性**：主教材构成学习路径的骨架；外部材料不能无标记地改变课程主线。
- **学习完整性**：不能因只生成“看起来重要”的知识而丢失必要前置关系、关键证明或例题角色。
- **可迭代性**：抽取、生成、审核和重生成应可分阶段执行，失败不应要求从头丢弃全部产物。
- **可解释性**：每个 Agent 的职责、输入、输出和审核依据应清楚；不能依赖不可见的隐式状态。
- **可验证性**：POC 应允许人工抽样和自动规则共同验收，不以单一模型评分作为唯一依据。
- **安全与版权边界**：原始教材和外部资料按用户授权使用；输出保留来源，不设计绕过访问控制或版权限制的能力。

## 7. 核心不变量

1. 没有可接受的 Learning Blueprint，就不进入完整内容生成。
2. 没有来源定位的关键事实、公式、定义和例题不得被标记为已核实。
3. 补充内容必须关联至少一个知识单元，并标明其不是主教材原文。
4. 审核结果不能被重生成静默覆盖；每次重生成都产生可区分的版本或运行记录。
5. 主教材、补充教材和外部资料的角色必须可区分。
6. Agent 数量不是验收指标；任务边界和质量结果才是。

## 8. 已确定的技术约束

- P0 输入为文本型 PDF，保留页码/块级来源；扫描 OCR、EPUB、HTML 和复杂版面为后续扩展。
- P0 后端为 Python 3.12 + FastAPI + Pydantic v2；Agent 工作流为 LangGraph。
- P0 前端为 Vue 3 + TypeScript + Vite，使用 shadcn-vue + Tailwind CSS 作为组件和样式基础。
- P0 的规范输出为 JSON Document IR，由受控 Vue renderer 呈现；Markdown 仅作为节点内容或导出格式。
- 模型接入必须支持 OpenAI API，以及基于 OpenAI-compatible API 的 Ollama 和 vLLM。
- P0 使用 SQLite + SQLAlchemy 2 + Alembic 和 SQLite FTS5，不要求向量数据库。
- P0 不引入 Celery、Redis 或其他分布式任务基础设施；使用 FastAPI + 本地 worker/CLI。

- SQLite FTS5 在评估样本上的召回不足时，是否引入 embedding 和向量数据库？
- POC 的默认云端模型、本地 Ollama 模型和 vLLM 模型分别是什么？
- P1 是否需要将接受后的 IR 导出到 VitePress 静态站点？
- 何种问题必须人工批准才能发布？
- 生成内容和教材原文的引用粒度、版权展示和保留期限如何规定？
